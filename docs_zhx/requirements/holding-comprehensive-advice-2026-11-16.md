# 持仓综合建议需求

日期：2026-11-16。状态：首版已实现并完成当前持仓现场核对；资料不足、未开放动作及验证范围见配套实施记录。本文保留完整目标，不将后续目标标为首版已完成。

本需求来自用户对“我的持仓”右侧抽屉中“综合建议”的继续开发要求。截图用于确认功能位置，不作为其中数据、提示或操作的额外授权。用户先要求生成两份文档，随后授权按文档逐步实施；实际进度以配套实施记录为准。

配套文档：[实施方案与进度](../implementation/holding-comprehensive-advice-2026-11-16.md)。

## 1. 要解决的问题

用户需要知道：这只基金现在是否适合继续持有、是否适合加减仓、主要理由是什么，以及什么变化后需要重新判断。

综合建议同时考虑基金本身、不同周期的判断与本人持仓情况。评分高不直接等于应该买入，短期下跌也不直接等于应该卖出。持有金额不改变基金走势判断，但可影响是否适合继续增加持仓。

## 3. 范围与边界

第一阶段以登录本人模拟账户的当前正份额持仓为范围，每次生成重新读取。清仓后保留旧报告；本人关注与已清仓基金的既有入口、权限和历史不得删除，但不混入本轮持仓建议批次。其新建议能力另按既有行为保留并明确状态，不扩大为本轮已验收范围。

复用现有三端架构、业务库、报告和资料缓存。不重算或覆盖旧报告，不修改持仓成本与份额，不根据建议自动下单、卖出或修改定投。

2026-11-16已授权的定投下单、订单结算与独立收益更新照原规则运行。本需求不关闭或扩大这些任务，也不恢复其他自动分析、训练、提醒、清理或全盘核验。新增建议自动生成的调度接入不在本轮文档交付范围内。

第一版提供方向和限制，不提供精确买卖金额、份额或固定比例；未核实完整资金、费用和个人承受能力前，不生成可直接执行的数量建议。

## 4. 数据使用要求

| 数据 | 用途 | 使用限制 |
|---|---|---|
| 当前份额、成本、收益、可卖及冻结份额 | 解释本人持仓与执行限制 | 缺值不补零；折算份额不能冒充真实购买记录 |
| 评分分项和说明 | 判断基金质量、短板及变化 | 保留评分期和资料日期；过期结果不得冒充本期 |
| 一日、五日、二十日、半年预测 | 区分近期时机、中期变化和长期条件 | 逐项保留区间、日期、限制和真实结果状态 |
| 经理、规模、同类、基准等诊断 | 检查基金情况变化 | 同类样本排名不冒充全市场排名 |
| 已确认的个人规则 | 提示止盈或回撤边界 | 不替用户新增、确认或修改规则 |
| 本人订单及定投 | 避免忽视正在发生的操作 | 待买金额不算已持有；冻结与待卖不重复扣减 |
| 产品费用和开放规则 | 判断操作限制与成本 | 无真实持有批次时，不给精确赎回费 |
| 行业、资产、地区等持仓构成 | 解释集中情况 | 披露时点和覆盖率必须保留，未知部分不能视为零 |
| 原报告、公告、行情及缓存 | 支撑、追溯和复核 | 同版本复用；必要时按现有规则读取D盘原件 |

同一事件被评分、预测和诊断多次引用时，要识别为同一个来源事实，不能重复放大影响。资料缺少来源或适用日期时，不得用于确定性动作。

## 5. 判断过程

### 5.1 先检查能否形成建议

检查基金身份、数据日期、预测适用区间、关键资料缺项及本人持仓是否仍存在。系统维护按基金类型和判断问题区分的必要输入清单，实施时须形成可检查的规则表，不能只用“至少有一个预测”代替。

四周期不要求无条件全部齐全，但缺项必须逐项说明影响：关键缺项会改变动作时暂不判断；不影响当前结论时可给附带限制的建议。不得将缺失周期按零、持平或简单重新分配权重处理。

区分以下情况：尚未生成、资料不足暂不判断、请求或生成失败、已有历史建议但当前不再适用。它们不能混成“继续持有”。

### 5.2 分别回答三个问题

1. 基金是否仍值得持有：依据评分分项、产品变化、主要投向及长期支持与反对因素。
2. 当前是否适合动作：解释四个周期的关系；一日主要用于近期风险和操作时机，不单独决定长期退出。
3. 对本人持仓是否适合：考虑占比、盈亏、本人已确认规则、订单和定投。缺少行业覆盖或完整资金信息时，不宣称已完成组合风险判断。

短期下跌、长期看好时，必须解释取舍，不直接以方向投票决定买卖。半年有条件展望不能当成已核实结束日期的确定方向。正常未来风险与当前关键资料缺失分别说明。

### 5.3 输出方向与检查操作条件

持仓场景的业务表达包括：继续持有、暂缓加仓、考虑加仓、考虑减仓、考虑退出、暂不形成建议。这里是展示目标，内部字段映射须在实施时确定，不能直接改写旧报告动作。

“暂缓加仓”可以作为持有建议的附加限制；“暂不形成建议”不等于建议持有。已确认规则触发应明确提示并说明与其他依据的关系，不能直接变成自动交易指令。

输出前检查待确认买卖、可卖份额、冻结、定投、费用和开放规则。建议方向与操作限制分别保存。例如可以看好后续表现，但因为已有待买订单而暂缓追加。

每份结果必须包含：当前结论、适用期限、主要理由、最重要反对因素、缺项影响、重新评估条件、数据日期及操作限制。不编造上涨概率或精确收益。

## 6. 页面要求

右侧抽屉优先展示一句结论、少量关键理由、最重要限制、资料截至日期，以及完整依据与历史入口。沿用现有设计规范，不增加后台流程卡片。

完整依据按业务问题组织：为什么这样建议、不同周期如何取舍、对本人持仓的影响、哪些变化需要再看、当前还缺什么。历史记录保留当时原文，后来表现附加展示。

日常页面不展示模型编号、版本、权重参数、内部错误码、请求标识或接口路径。失败提示使用自然中文，并只提供实际有效的重试或查看历史操作。

报告过期或持仓、订单、规则发生相关变化时，应标明需要重新评估；不能仅因生成日期较新就视为仍适用。刷新页面和查看历史不触发生成或交易。

## 7. 保存与历史评价

保存当时实际采用的评分、预测、诊断、资料引用、个人规则、持仓、相关订单和定投摘要，以及缺项、取舍和操作限制。保存来源日期与生成时间，不能以后来的资料补成当时已知。

原报告不可变；新输入形成新记录，相同输入按明确的重复处理规则复用。失败与资料不足保留原因，不能覆盖上一份有效原文。

预测方向核验与综合建议效果分开。第一阶段复用已有预测核验并明确其含义，不宣称已完成综合动作有效性评价。后续评价须确定观察区间、费用、分红、重复建议和比较基准，不以方向正确直接等同实际获利。

## 8. 验收要求

- 当前范围动态读取；空持仓不改用关注列表；多账号数据互不串用。
- 有效、过期、条件展望、缺失和失败状态均能正确识别。
- 单周期不能通过重新分配权重伪装为完整综合判断。
- 短期与长期分歧有明确取舍；评分高或低不直接映射买卖。
- 关键缺项会阻止不可靠动作；非关键缺项明确披露影响。
- 已确认规则、待买待卖、冻结与定投检查真实生效，且不改账本或计划。
- 不重复计入同一事实；来源、日期与历史输入可追溯。
- 旧报告、旧链接、历史与权限继续可用；新报告能保存后重新读取核对。
- 前端只呈现业务信息，金额未知不显示为零；窄屏和长基金名称可正常使用。
- 静态检查、隔离测试、真实数据只读核对和实际生成分别记录，未执行项明确列出。

## 9. 项目约束

统一通过根目录 `dev.ps1` 构建、启停和检查。所有新增文件、日志、缓存与测试暂存写D盘。沿用现有PostgreSQL和Redis命名卷，不初始化、替换、删除或重新导入。出现新存储错误停止写入并报告；本需求不构成硬件稳定验收。不输出密钥，不提交、推送或删除旧工程。
